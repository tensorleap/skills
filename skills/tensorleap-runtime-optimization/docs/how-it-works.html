How the runtime optimization skill works

The skill takes a working Tensorleap integration from “it’s slow and nobody knows why” to a measured, component-by-component picture. It applies every change the evidence supports that leaves the outputs identical, can check the result on a Tensorleap server, and writes a report naming what limits runtime and memory now.

Measured the way Tensorleap runs itEach component runs in its own fresh process, on the data shapes and order the platform uses.
Scored against the modelEvery cost is a multiple of the model’s own inference time per sample: the floor.
Lossless unless you say yesA change stays only if every output is identical and it is faster or smaller.
Evidence before conclusionEach claim carries its measurement and, on the server, the log lines it came from.

At a glance

What you give it

  • A working integration at the repo root: leap_integration.py and leap.yaml.
  • The Python environment that runs it (poetry by default).
  • Optionally, a Tensorleap server, for the validation push and the online diagnostics.

What you get back

  • The optimized code: one git commit per fix, or fixes/NN.patch files when the repo has no git.
  • optimization-log.md: every candidate, the evidence, what was tried, the verdict.
  • report.md and report.html: Part 1 offline, Part 2 online when diagnostics ran.

Everything the skill measures comes from one tool, tl_perf.py, run inside the integration’s own environment. The agent reads code, reasons, and makes one change at a time; tl_perf decides whether the change stays. Artifacts go to tensorleap/runtime-optimization/ in the integration repo.

The whole flow

Eight phases, in order. Each one ends at a gate that must pass before the next starts. The loops of Phase 4 repeat until no candidate is worth another try.

How Tensorleap runs your code, and why it matters

Tensorleap does not run an integration as one script. It runs its pieces in separate worker processes, on batches or single samples, in an order you don’t control. An optimization is real only if it helps there, so the skill measures under the same conditions.

How the platform runs itWhat that means for a fix
Encoders and metadata of the same sample run together, in one processA small cache they share is the standard lossless fix for repeated work
Visualizers run later, one sample at a time, in a process where nothing else ran firstThey must be efficient on their own; they never see caches from encoders, metadata or metrics
Metrics and loss run on batches, in their own process, fed the batch’s tensorsA cache warmed by encoders doesn’t help them; a metric that reloads source data should compute from its tensors
Samples are not processed in preprocess orderPer-file caches over a flat sample list mostly miss; group samples by file instead
Preprocess runs again in every worker processKeep it light; its memory and time are paid once per worker
Dataset code runs on CPU; only the model uses the GPUA slow encoder is CPU work, whatever GPU the server has
Caches are per worker processTheir memory multiplies by the number of workers; keep them small

The cost model. Every component is scored by its mean cost per sample relative to the model’s mean inference time per sample. A component at 450× the floor limits the run; one at 0.01× is noise, however ugly its code. For memory, the unit is the footprint of the integration’s own code in one worker process: imports, globals, the preprocess result, caches. Every worker pays it.

PHASE 0

Preflight and setup

What it checks

  • The integration’s own Python environment, found from pyproject.toml or requirements.txt.
  • Devices, and whether the model actually runs on the GPU when one is present.
  • code-loader version and features (grouped preprocess needs ≥ 1.0.196).
  • That the integration passes the dataset check and the model loads on its own.
  • Free disk and how busy the machine is. Separately, whether a server is reachable for Phase 6.

What it can catch

  • A GPU that is there but unused: the model silently on CPU (catalog R, exit 4).
  • An integration that doesn’t work yet (exit 3): optimizing stops until it does.
  • A model that only loads inside the platform (exit 6).
  • A busy machine that would skew every timing.

How

tl_perf preflight runs inside the integration’s environment, loads the model, runs the dataset check and probes the devices. It writes preflight.json and answers with an exit code the skill acts on. perf_preflight.sh checks the leap CLI, login and server without blocking the local work.

Why

Every later number is only as good as the environment it was measured in. A floor taken on CPU when the server has a GPU changes every ratio in the report. In a git repo, the skill also asks before mixing your uncommitted work with its own changes, then works on its own branch.

From the test integrations

  • All nine blind runs passed preflight with a “CPU floor” note: the test machine was a 16-core laptop CPU with 64 GB of RAM and no GPU.
  • DET-128: a fixed model batch of 1, read from the input shape [1,3,640,640]. An earlier tool version took the model as dynamic and would have tried batch sizes the model rejects.
  • TS-480: a warning of load 8.0 on 16 cores and under 20% of RAM free.
  • Why the load warning exists: on a busy machine, one early run measured the floor at 2.98 instead of 1.42 ms per sample, and the recommended batch moved from 4 to 16.
PHASE 1

Floor and fit

What it checks

  • floor: the model alone, after a warm-up, at several batch sizes: P50, P90, P95 and P99 per batch, and the batch size where throughput stops improving much.
  • fit: per-sample tensor size, rows per state, the model’s measured memory per batch size, and whether every metric and the loss accept a batch.

What it can catch

  • A metric or loss that fails on a batch (catalog D). The local integration test runs batch 1, so it never shows this; the platform does.
  • A configured batch size past the throughput knee, or one that won’t fit in memory (exit 5).
  • Huge per-sample tensors, debug flags, full-dataset work in preprocess.

How

Times inference with nothing else running, sweeps batch sizes to find the knee (and says when a larger sweep is needed), measures memory per batch, and calls each metric and the loss with a real batch. The floor is the mean inference time per sample at the recommended batch size.

Why

The floor is the unit every later cost is expressed in. A component at 1× the floor matters; one at 0.01× doesn’t. This phase also records your words about memory (out-of-memory, “memory-heavy”, nothing) and the priority: memory first by default, runtime first only when you say speed matters more.

From the test integrations

  • IMG-480: 4.20 ms per sample at batch 1, 1.54 at batch 4 (the knee), 1.27 at batch 64. Floor: 1.545 ms per sample. Two measurements on a quiet machine agreed within 1%.
  • PARQ-70k: the knee wasn’t reached by batch 64. A wider sweep found batch 256 at 0.078 ms per sample; batch 512 was no faster (0.081).
  • Batch support: PARQ-70k’s loss failed on a batch of 2 (“broadcast (2,10) (2,)”) and worked only at batch 1 and 10; it was fixed first. DET-128’s ground truth broke when stacking images with 1 to 42 boxes.
  • DET-INST: 19.7 MB of tensors per sample and a model that rejects batch 2, so the server push used batch 1.
PHASE 2

Read the code

What it checks

Preprocess, every encoder, metadata function, metric, the loss, every visualizer, and everything they call.

What it can catch

  • One component calling another’s function, or the same file opened by several components.
  • Python loops over rows, per-call model or table loading, per-sample list.index.
  • Debug statistics on large arrays, unbounded caches, unseeded randomness.
  • Round trips between representations (PIL ↔ numpy, float64 ↔ float32, DataFrame ↔ dict).
  • Imports evaluation never uses; heavy imports only one visualizer needs.
  • Bugs: code wrong for some shapes or batch sizes, silent except: blocks.

How

The agent reads the code and writes each tell to static.json with the component, a catalog class and a one-line message. A tell raises the confidence of a measured candidate. It never creates a candidate by itself.

Why

Measurement says where the time goes; the code says why. Data-dependent branches are noted separately, because the equivalence check covers only the branches the sampled data executes.

PHASE 3

Baseline profile and score

What it checks

  • Sample generation (encoders and metadata together, per sample).
  • Metrics and loss, in their own process, on batches.
  • Visualizers, in a fresh process, fed the sample’s tensors.
  • Per-worker start-up: imports plus preprocess.
  • Diagnostics: hot functions, repeated calls, file reads per sample, a sorted-order what-if.
  • An output snapshot of every component, and the integration’s memory.

What it can catch

  • Components that crash on some samples or can’t be wired (exit 7).
  • Outputs that differ between two runs of unchanged code (catalog T).
  • Which share of the expected runtime is generation, inference, metrics, visualizers or start-up, and the generation-to-inference ratio.
  • Work repeated across components, cache thrash, per-call loading: the catalog classes.

How

tl_perf profile (200 samples per state and 50 visualized samples by default) runs each pass in a fresh process. The first run becomes the baseline for equivalence and is taken twice to detect nondeterminism. tl_perf score ranks candidates by expected seconds removable × confidence, with the evidence for each.

Why

A fair, repeatable baseline makes every later verdict meaningful. The ranking comes from measurement, so a problem the catalog doesn’t describe still rises to the top. The agent then finds its cause from the hot path and logs it as new.

From the test integrations

  • DET-TIFF baseline: generation 219.2 ms per sample (metadata 132.3), inference 21.9, two metrics at 44.9 and 44.1, visualizers 6.1, start-up 0.91 s per worker. Generation was 64% of the expected runtime. The same file was read 5 times per sample, exactly what the code reading predicted.
  • PARQ-70k: 1.00 file reads per sample in the platform’s order against 0.03 in sorted order, and generation 0.697 against 0.175 ms: cache thrash from the storage layout (class B).
  • TAB-3.7M, where percentiles matter: generation mean 2.263 ms, but P50 0.29 and P95 10.2 ms. Unlabeled samples cost 5.84 ms against 0.26 for labeled ones: a membership check scanned a 2.6M-element list for every unlabeled sample.
  • score on IMG-480 ranked a metadata function first: 19.6 ms per sample, 13.7× the floor, 9.42 s expected, confidence 0.80. It re-invoked an encoder and read the same file up to 3 times. Confidence starts at 0.5, gains 0.3 with profile evidence and 0.2 when the code reading agrees.
  • Why the process boundaries matter: when an early tool version ran metrics inside the generation process, a shared cache made one metric look 95 → 8 ms. In its own process, the same fix gave 95 → 52 ms, and a separate fix was needed to reach 8.6 ms.

Memory measurement and triage

The memory unit is the user-code footprint of one worker process: what the integration’s own code holds (imported libraries, module globals, the preprocess result, caches, per-call temporaries), measured with the model not loaded. The profile splits it by holder and by stage, notes how much more preprocess needs at its peak than it keeps, and marks the unattributed part (memory freed but kept by an allocator) so nobody chases it.

StatusWhenWhat happens with runtime first
REDOut-of-memory reported or seen, or one worker’s footprint over half the memory budgetMemory loop first; a memory fix may cost up to +15% runtime
AMBERA large footprint, a structure over 1 GB per worker, or growth with the samplesRuntime loop first, then memory fixes within noise (3%)
GREENNone of the aboveRuntime loop, then only free memory wins

By default memory is the priority: the memory loop runs first and a memory fix may cost up to +15% runtime, because a smaller footprint usually also makes the run faster (more workers fit, no out-of-memory restarts). The report leads with memory only where there is memory pressure.

From the test integrations

  • TAB-3.7M: 16.02 GB per worker, the peak set inside preprocess (10.06 GB kept plus 5.88 GB transient). The request said “run out of memory”: RED. Repeat measurements differed by 0.3%.
  • TS-110k (the time-series integration at 110k rows): 1.56 GB, of which the preprocess result is only 0.04 GB. The request said “a lot of memory”: AMBER.
  • DET-128: 0.23 GB, GREEN, no candidates. Run-to-run spread stayed under the 64 MB minimum gain, and early growth was correctly not called a leak.
  • A miss that changed the skill: on BIO-258k the request said “workers use a lot of memory”, but the agent scored it GREEN. The skill now quotes every memory phrase in the request and maps it to out-of-memory, high or none.

Import check

The profile records which stage really runs each third-party package (preprocess, generation, metrics and loss, visualizers). It times each candidate import alone in a fresh interpreter, for memory and seconds, and lists imported names its files never reference.

  • Unused: imported, but no stage ran it. Remove it; every worker pays its import memory and time for nothing. It is a memory candidate and a start-up candidate at once.
  • Lazy: only the metrics or only the visualizers run it. Import it inside them. That keeps it out of every worker’s start-up memory, but each worker still imports it once, so it counts as memory, never as a runtime gain.
  • Names never referenced: cosmetic, tidied only alongside a real fix. Packages under 20 modules are not worth a change.

From the test integrations

  • BIO-258k: a helper module imported for one unused name pulled in heavy libraries costing 110, 64, 47 and 29 MB alone. Removing it took the footprint from 1.73 to 1.63 GB per worker and start-up from 2.66 to 1.92 s; runtime −1.2%.
  • PARQ-70k: moving the deep-learning framework import into the model loader took the footprint from 0.58 to 0.35 GB (−40%) and start-up from 1.51 to 0.49 s. Importing a table library only where needed saved 48 MB, under the 64 MB minimum, so it was rejected (exit 9).
  • Both fixes came from the earlier unused-import finding that this check extends. A package used only at import time, or only through another library, can still look unused: the agents caught two such cases before acting.
PHASE 4

Lossless loops: memory (4M) and runtime (4R)

The core of the skill. One candidate, one change, one measurement, one verdict, repeated until no candidate is worth another try. The memory loop runs first by default; with runtime first, the memory status decides the order.

What it checks

For each change: are all outputs identical to the baseline, and is it faster (4R) or smaller (4M) than the last accepted run?

What it can catch

  • A “fix” that changes outputs (exit 8).
  • A change that doesn’t matter: under 5% faster, or for memory, under max(5%, 64 MB) smaller (exit 9).
  • A runtime fix that grows the footprint over 10%, or 5% when memory is AMBER or RED (exit 10).
  • A memory fix that costs more runtime than allowed (exit 12).

How

  1. Pick the top candidate worth it: at least 1× the floor, or at least 10% of the expected runtime.
  2. Explain why it is slow or large, from its evidence and the code. No explanation, no change.
  3. Change one thing, from the catalog or the levers. A cache is used only where Tensorleap shares it.
  4. Measure with profile, then compare.
  5. Decide on the exit code.

Why

One change per measurement keeps every verdict attributable. A change that wins only in sorted order depends on processing order and isn’t delivered on the platform, so the skill prefers changes that win in both orders.

What “lossless” means

  • Bit-identical by default, for every input, ground truth, metadata value, prediction, metric, loss and visualizer output on the snapshot samples. A tolerance is allowed only with a stated reason, such as a reordered float sum, and goes into the report.
  • Nondeterministic outputs are checked by distribution and reported. Seeding them changes behavior, so it is your decision.
  • Only exercised code is verified. Branches the snapshot samples never run are listed as coverage caveats.
  • No claim of equivalence is trusted, whether a commit message or “it should be the same”. Only compare decides.
PHASE 5

Options that change outputs

When

Only if, after Phase 4, one component still dominates (roughly more than half the expected runtime, or many times the floor) with no lossless fix left. Or memory is still RED or AMBER and the remaining holders can only shrink by changing values.

What it offers

For example: work at lower precision or resolution than the outputs need, narrower dtypes that round, fewer visualizers of the same source, dropped columns an output reads. Each comes with what changes, the expected gain from the profile, and the cost.

How

Asked once. Only what you accept is applied, one commit each, and compare must show that only the declared fields changed.

Why

Speed bought by changing results is your call, never the tool’s. Declining every option is a valid, recorded outcome.

From the test integrations

Every test run was unattended, so no option was accepted and none was applied. What was offered:

  • BIO-258k: compute the loss from the latent it receives instead of re-running the model: 2.8 → about 0.03 ms per sample, about −30% of the runtime. Loss values change at rounding level.
  • TAB-3.7M: merge or drop 101 metadata fields: about −60 to −75%. Those columns disappear from the analysis.
  • DET-TIFF: decode at reduced resolution: up to about −50%. Input pixels, and so predictions, change.
PHASE 6

On the Tensorleap server

Two modes. 6A smoke validation is the default and proves the optimized integration still works on the server. 6B online diagnostics also measures what limits the run there, from the run’s own logs. It is long and server-heavy, so it runs only after you say yes when asked (6.0), and never when the skill runs unattended. Diagnostics read the run; they never change server settings.

6A · Smoke validation

What it checks

Every component runs on the server without errors, and the Evaluate reaches a terminal state.

What it can catch

Problems the local run can’t see: a data path that differs on the server, a credential not injected, a file missing from leap.yaml’s include, a dependency missing from requirements.txt, a server-side rejection.

How

Caps each state to about 50 samples in place on the accepted code, pushes and evaluates, then removes the cap with tl_perf restore once the code is uploaded. It writes the report before waiting, then watches that Evaluate. A server-side rejection gets exactly one retry.

Why

A fast integration that fails on the platform is worth nothing. The smoke run takes minutes and doesn’t measure runtime; Phases 1–4 did that.

From the test integrations

  • 8 of 8 smoke Evaluates finished in the six-integration validation round.
  • TAB-3.7M: the first push failed. A new sample-id class couldn’t be unpickled on the server, where the integration isn’t importable. After a correctness fix, the re-push finished in 2 min 50 s with 150 of 150 samples. The smoke push caught a bug that every local check had passed.
  • DET-INST: the server rejected the Evaluate at creation. The one retry finished: 287 of 287 rows in 3 min 20 s.
  • The one-retry rule came from testing: against a broken server, an early version pushed 5 times.
  • Unattended runs stay in smoke mode: the PARQ-70k blind run recorded "mode": "smoke", "authorized_by_user": false, and its smoke Evaluate finished in 53 s on 100 samples.

6B · Online diagnostics

With your yes, the skill pushes the whole dataset, or a per-state cap you give for a shorter test run (like the integration skill’s sample_limit_per_split). It follows that one run and reads its logs. The analysis covers the evaluation, with the start-up that leads into it, and the visualization. The platform’s analysis after evaluation (post-processing) appears as one row of time and is not analyzed.

What it checks

  • Each phase’s warm-up, steady pace and tail.
  • Per-component statistics with percentiles, over the steady window only.
  • Who waits on whom, and whether that is on the critical path.
  • Memory per pod: peaks, limits, restarts, out-of-memory.
  • Online against offline: inference, generation, metrics, visualizers, memory.
  • Whether the server’s CPU, memory, worker and GPU settings fit the run.

What it can catch

  • Which side sets the pace: sample generation, metrics, the model, or work on the evaluation pod.
  • A visualization paced by one serial worker, or visualizers run twice per sample.
  • Work repeated per row that could run once per sample, or once per batch.
  • A server that runs the same code many times slower than your machine.
  • Another run sharing the server, which slows this one.
  • Settings that limited the run, or sat mostly unused.

How

online collect keeps the merged logs under online/ with identity fields removed, resumes after any interruption, records other runs in flight and why a run failed. online analyze turns them into online/analysis.json; tl_perf report renders it.

Why

Locally, the skill can only model the platform. Online, it sees the real run: worker counts, the server’s speed, data movement between pods. A claim about the platform needs that evidence.

From the test integrations

  • DET-INST: 28 polls over 16 pods with no gaps, resumed twice while the run was live. The evaluation pod’s kept log was 4,570 lines, complete from its start: more than twice the 2,000 lines the CLI returns per pod.
  • BIO-258k: 764 polls and 3 gaps over 6.3 hours. Another push shared the server for about 4 hours, and the report says so.
  • A guard that came from a mistake: a suspected stall every 11 seconds was the server logger’s rate limit. Rate-limited lines are now dropped before anything is counted.

Finding the steady pace

Tensorleap adds workers while an evaluation runs, so the first minutes are slower. The evaluation and the visualization each speed up on their own. Statistics count only once a phase’s pace stops rising.

The visualization stop (exit 21) needs a steady pace over enough samples: a fifth of the visualization, at least 200 and at most 1,000. Stopping must also save at least a quarter of the samples and at least 5 minutes. A short or nearly finished visualization runs to the end; the analysis then projects the full visualization time from the steady pace.

From the test integrations

  • TAB-3.7M evaluation: warm-up 120 s, then 96.38 rows/s for 300 s (5 windows, 1 worker, 58% of the phase), tail 97 s. Its visualization: warm-up 300 s, then 1.70 samples/s for 3,720 s (91% of the phase).
  • BIO-258k, a 6.3-hour run: 14 early plateaus at 2.91–3.70 rows/s over about 109 minutes, while workers were still being added, counted as warm-up. Steady: 22.78 rows/s for 52 minutes with 6 workers. The tail ran at about 10 rows/s while another push shared the server, and the report says so.
  • Not reached: DET-INST’s evaluation moved between 2.30 and 6.71 rows/s over 186 s; DET-TIFF’s phases were shorter than three 60-second windows. Both matched expectations written before the runs.
  • Stopping early: on TAB-3.7M the rule asks to stop at 1,526 of 10,000 visualized samples, saving about 85 minutes. In the real run the user stopped at 6,940; the analysis projected about 5,866 s for the full visualization (4,069 s measured). DET-INST (688 visualized samples) and DET-TIFF (359) were never asked to stop.

What sets the pace of the evaluation

One evaluation step is pull a batch, then infer, extract embeddings and hand off the metrics. Over the steady window, the shares of that loop say who waits on whom.

From the test integrations

  • Inference floor, DET-INST: inference 97% of the loop, waiting for samples 0%, workers idle 97%. Pod CPU readings agreed independently: the evaluation pod used about 4.7 cores, all 6 workers together about 2.0.
  • Metrics-bound, owned by the integration, BIO-258k: inference 58%, waiting 5%, metrics hand-off 35% of the loop, with 1,826 back-pressure waits totalling 1,856 s. The 6 workers used 12.1 cores, the evaluation pod 0.9. The cause: the integration’s loss re-runs the model, which ran about 19× slower on the server.
  • Metrics-bound, not your metrics, TAB-3.7M: hand-off 21%, output conversion 52%, waiting 15%. The user’s metrics and loss took 0.28 ms per batch against 2.11 ms of hand-off wait, so the report says the metrics pipeline limits throughput, not the user’s metrics.
  • Close behind, DET-TIFF: an inference floor with sample generation close behind (17% waiting). Online inference was 6.6× slower than offline (140 against 21 ms per row), generation only 1.5×.
  • No full diagnostics run ended producer-bound. Expectations written beforehand predicted it for two integrations; the measurements showed why it didn’t happen.

Root causes and mechanisms

For each phase that took at least a tenth of the run, the analysis builds a root cause: which side set the pace, where that side’s time went, the mechanism, the part to change, what is ruled out, how much of the phase is explained, and a confidence. Links inferred rather than measured are marked.

Under each root cause, generic rules list the mechanisms they find in that phase’s own measurements. The rules read shapes, not known problems:

RuleLooks for
Who waits on whomA hand-off one side waits on, on the evaluation’s own thread
Dominant stepOne step that takes most of a phase
Count × unit costWork done once per row where the unit is a sample or a batch
Repeated workThe same data loaded, generated or computed again
Growth over timeMemory or a backlog that keeps rising
Serial work beside idle capacityOne core of many, one busy pod among idle ones

From the test integrations

  • TAB-3.7M visualization (76% of the run, 94% explained): the evaluation pod waits 582 ms per batch, 99% of the phase, while one worker process spends 85% of its time rendering. Repeated work: the heatmap overlay re-runs two of the user’s visualizers on the same input (13,600 calls each), 1,605 s or 39% of the phase. Serial work beside idle capacity: the workers setting the pace used 1.0 of their 4 cores. Ruled out: queue back-pressure (1.9 s).
  • DET-INST visualization (40% of the run, 96% explained, measured): 265 forward passes × 585 ms on CPU = 155 s, 86% of the phase, while the workers were busy 23% of the time. Off the pace: each object row regenerated its source sample to fetch a mask (505 rows × 40 ms), and the mask applied only 20% of the time.
  • TAB-3.7M evaluation: count × unit cost: 46,335 steps × 8 ms of per-step work around a 1 ms forward pass = 354 s, 68% of the phase, the largest part output conversion at 5 ms per step. Repeated work: a replaced worker pod loaded the integration again (38 s) while the evaluation waited 60.7 s for samples.
  • Forward passes per source sample: in a replay of DET-INST with one of the platform’s own optimizations turned off, the rule found 944 passes for 261 source samples, 3.6 per source. The 683 extra passes × 730 ms = 498 s, 63% of the evaluation. This rule exists because the first version could only say “the forward pass is slow”.

Server settings, the floor, and offline against online

  • Server settings: what each pod got (CPU, memory, worker pods and processes, GPUs) against what the run used, with a verdict: limited the run, at its limit, fits, or mostly unused. Advice is given for automatic and for manual resource settings. CPU is judged during the evaluation and the visualization; memory over the whole run, since a limit has to hold every step.
  • Gap to the floor: the steady online time per row against the offline floor. A gap close to the inference slowdown means the model runs slower on the server, not that there is overhead around it.
  • Offline against online: the same components measured both ways. A large ratio says the server differs from the machine the optimization ran on.

From the test integrations

  • TAB-3.7M: worker pods × processes, 2 × 1, limited the run: the workers set the visualization’s pace and their count didn’t grow. Evaluation-pod CPU, 16 cores with 1.11 used at P95: mostly unused. Worker memory, 19.0 GB with a 9.3 GB peak: fits.
  • DET-INST: no GPU limited the run, since inference sets the pace and ran on CPU. Worker memory, 2.0 GB with a 0.3 GB peak: lower toward 0.4 GB.
  • Gap to the floor: DET-INST about ×1.6–1.8. On the first run that matched the model’s own slowdown on the shared machine, so the gap was the model running slower, not overhead. BIO-258k: 43.9 against 1.0 ms per row (×43.8), with inference alone about 19× slower online. TAB-3.7M: 10.4 ms per row against a model of about 0.001 ms; about 8 ms of per-step work surrounds each forward pass.
PHASE 7

The report

Part 1 · Offline

Always present. What limits the integration’s own code, what was changed (each fix with its catalog class, before and after per sample, and its memory effect), the trade-offs between memory and runtime, what remains and who owns it.

Part 2 · Online

Only after an approved diagnostics run; otherwise one line saying it was not run. The primary bottleneck with log evidence, root causes, server settings, memory per pod, the gap to the floor, and what to ask Tensorleap for.

How it reads

Each part is answer-first, with details in a collapsed appendix. Part 2’s appendix keeps the per-component percentiles from the server. A part leads with memory only under memory pressure, otherwise with time.

What you share

report.html: one self-contained page that can be mailed or posted as is. It ends with every step that ran and the artifact it left. report.md holds the same content as text.

From the test integrations

The two-part report for TAB-3.7M, after its diagnostics run:

  • Memory leads Part 2: the server warned that the job “needs 36.0 GiB, 35.8 GiB free”. The first card: the worker pod peaked at 9.3 of 19.0 GB, almost all of it the integration’s own memory (offline peak 10.5 GB).
  • Where the time went: visualization 76%, post-processing (not analyzed) 11%, evaluation 10% of 5,345 s.
  • The two parts reconcile: Part 1 had blamed sample generation, assuming 1,000 visualized samples; Part 2 notes this run visualized 6,940 of 10,000.
  • On BIO-258k, with no memory pressure, Part 2 opens with “No memory pressure on this run, so time leads this part.”
  • The two-part layout cut the TAB-3.7M report from 10,252 to 8,421 words and from 28 to 20 headings.

Code history without git

The skill keeps, undoes and shows its changes with any version control, or none.

  • profile saves the integration’s code; an accepted compare writes the fix as fixes/NN.patch. Changes made before the baseline become fixes/00-before-baseline.patch.
  • tl_perf restore undoes what wasn’t accepted, including the smoke or diagnostics cap, which is applied in place and never committed.
  • The cap guard reads config files too (.yaml, .toml, .cfg, .ini), so a cap set through a config key is caught.
  • The report flags code that changed after the last profile.
  • In a git repo the skill also commits each accepted fix on its own branch, one commit per fix.

From the test integrations

  • PARQ-70k, blind run without git: fix 1 was accepted and written as patch 01. A later candidate was rejected (exit 9), and restore reported “code back to runs/002 (2 file(s) restored)”. The smoke cap was applied in place, pushed and restored, leaving no cap marker. Done in 695 s: expected runtime 257.5 → 181.0 s (−30%), memory 0.61 → 0.31 GB per worker, outputs bit-identical, smoke Evaluate finished (53 s, 100 samples). Applying the patches to the original code reproduced the final code exactly.
  • That run found a gap: a correctness fix made before the baseline (the loss failed on batches larger than 1) had no patch. It is now written automatically as 00-before-baseline.patch.
  • PARQ-70k, blind run with git: done in 530 s, with one commit per accepted fix (the pre-baseline correctness fix, an input fix at 0.979 → 0.108 ms per sample, a start-up memory fix at 0.58 → 0.35 GB per worker) and the report. Rejected candidates (exits 12, 9, 8, 9) were undone with restore.

What it never does

  • Keep a change that compare did not accept, or apply an option that changes outputs without an explicit yes.
  • Measure runtime with the integration test or a hand-written loop: only tl_perf models how Tensorleap runs the components.
  • Make a visualizer depend on a cache filled elsewhere, or assume a cache survives across worker processes.
  • Alter your source data or the model weights.
  • Re-push blind, or commit a smoke or diagnostics cap.
  • Run online diagnostics without your explicit yes, run them unattended, or change server settings.
  • Put secrets, credentials or data paths into the report beyond what your repo already contains.
  • Save memory by changing values without an explicit yes, or let a memory fix cost more runtime than allowed.
